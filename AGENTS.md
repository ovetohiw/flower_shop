## Стартовый воркфлоу

0. Синхронизация с remote (до чтения PROGRESS) — см. процедуру ниже. При hard на sync — стоп, работу этапа не начинать.
1. [PROGRESS.md](PROGRESS.md) — блокер и следующий шаг.
2. [FEATURE.md](FEATURE.md) — контракт активной фичи; поле `Exec plan:`.
3. Если в FEATURE указан `Exec plan:` — откройте эту папку и следуйте чеклисту [docs/exec-plans/index.md](docs/exec-plans/index.md) (plan → только текущий этап; без широкого discovery, если план заполнен).
4. [PLANS.md](PLANS.md) читайте только когда нужен **новый** план или меняется политика планов — не на каждый старт исполнения уже указанного плана.
5. UI-правки: сначала [refs/](refs/README.md), затем [docs/convention/UIDESIGN.md](docs/convention/UIDESIGN.md) и STACK. Доменные ограничения агента — [docs/convention/index.md](docs/convention/index.md).
6. Последние коммиты: `git log --oneline -5`.

Если текущая базовая верификация падает — чините её. Новую работу при неисправном стартовом состоянии не начинайте.

### Синхронизация с remote (шаг 0)

1. Если нет git-репозитория — hard (блокер в PROGRESS).
2. Если remote / upstream текущей ветки **нет** — записать в PROGRESS «sync N/A, remote отсутствует» и продолжить старт (push в конце этапа станет hard, если remote так и не появился).
3. Иначе: `git fetch` (upstream текущей ветки).
4. `git status`: грязное дерево с локальными правками **до** начала работы этой сессии → hard (не затирать чужое); чистое — дальше.
5. Сравнение с upstream: **behind** → `git pull --ff-only`; **ahead** → ок; **diverged** или `pull --ff-only` не прошёл → hard; сбой fetch/pull (auth/network) → hard.
6. Запрещено: `pull` с merge «наугад», `reset --hard`, force-sync без явной просьбы человека.

## Автономный цикл исполнения

Горизонт одного прогона — **только текущий этап** exec plan (или работа без плана в объёме FEATURE, эквивалентная одному этапу). Соседний этап в том же прогоне не начинать. Указатель «текущий шаг» в plan после закрытия этапа можно сдвинуть на следующий для handoff; исполнение следующего — следующая сессия или явный пинок.

```text
sync с remote (шаг 0 старта)
  → старт (PROGRESS → FEATURE → plan → только текущий этап)
  → цикл: сделать → проверить по DoD этапа → при fail: диагноз/fix
  → при зелёном DoD: commit этапа → push → handoff → СТОП
  → при hard: handoff без авто commit/push → СТОП
```

Правила цикла:

- Не ждать подтверждения на каждый шаг реализации внутри этапа.
- Не ставить этапу `готово` без полной схемы DoD этапа.
- Fail проверки → чинить в рамках этапа; после **2 неудачных** попыток на одну и ту же ошибку → hard-блокер (третья «наугад» запрещена).
- Soft-решение → запись в «Открытые решения» / лог plan (и в PROGRESS, если влияет на handoff) → продолжить.
- При зелёном DoD этапа — обязательные commit и push по процедуре ниже (без отдельного запроса пользователя). Mid-stage и выход по hard — без авто commit/push.
- Гейты DoD фичи / completed / ranking **не ослаблять**.

### Commit и push по готовности этапа

Только после зелёного DoD этапа (поля схемы заполнены; этап можно ставить `готово`):

1. `git status` / `git diff` — в коммите только файлы этапа (код + plan/decompose + PROGRESS; FEATURE если трогали); нет секретов ([docs/convention/SECURITY.md](docs/convention/SECURITY.md)).
2. Сообщение коммита: одна цель — закрытие этапа `{id}` / краткий смысл DoD (why), не «WIP».
3. `git add` релевантных файлов → `git commit`.
4. `git push` (или `git push -u origin HEAD`, если upstream ещё нет).
5. В PROGRESS: ветка, short SHA, факт push (или «push не выполнен»).
6. СТОП (соседний этап не стартовать).

Запрещено: `--force` / `--force-with-lease`; `--no-verify`; amend уже запушенного; push чужой ветки; коммит красного DoD или mid-stage.

Провал commit (хук) или push → hard в PROGRESS; при успешном commit и упавшем push — зафиксировать SHA и «push не выполнен»; этап не считать доставленным на remote.

Работа без Exec plan («эквивалент одного этапа»): то же commit+push при закрытии этого объёма.

### Soft vs hard

**Soft (решить и продолжить):** выбор реализации внутри контракта FEATURE и STACK; повтор уже принятого паттерна репозитория; уточнение из карты контекста / полей этапа «Читать» / «Менять»; точечный fix без расширения скоупа фичи, без которого DoD этапа не закрыть.

**Hard (стоп, блокер в PROGRESS, вопрос человеку — без тихого обхода):**

- нет git-репозитория; грязное дерево на входе сессии; diverged с upstream; сбой fetch / `pull --ff-only`;
- сбой commit или push при закрытии этапа;
- нужен выбор в STACK / архитектуре, которого нет;
- правка вне скоупа FEATURE или ломает зафиксированный контракт поведения;
- security-неоднозначность (секреты, доступ, обход защиты);
- нужны секреты / креды / действие человека вне репозитория;
- этап негоден к исполнению (пустые «Читать» / «Менять», однострочный этап);
- смена **смысла** этапа или цели plan (task/bug: запись + стоп; big-task: hot-fix только если не меняет смысл остальных этапов — иначе стоп);
- 2 неудачных фикса одной проверки.

Детали старта по plan — [docs/exec-plans/index.md](docs/exec-plans/index.md).

## Definition of Done

Канон готовности фичи. Доказательство — одна схема полей (критерий → команда/действие → результат → артефакт → дата/сессия). Шаблон заполнения — в [FEATURE.md](FEATURE.md) («Доказательства DoD»). Пустой или однословный блок («ок», «прогнано») готовность не подтверждает.

Уровни закрытия:

- этап exec plan — DoD этапа в `*-decompose.md` (объём этапа, не подмена DoD фичи);
- фича — пункты ниже + заполненные доказательства в FEATURE.md;
- смысловая работа с планом — `*-result.md` (секция «Верификация» по той же схеме) + запись в [docs/exec-plans/ranking/](docs/exec-plans/ranking/index.md).

Фича готова, когда:

- каждый критерий приёмки в FEATURE отмечен и имеет строку доказательства по схеме выше;
- каждый отмеченный уровень верификации в FEATURE (unit / интеграция / сквозной / health-check / базовая из AGENTS) прогнан: команда и результат записаны;
- базовая верификация из слотов ниже зелёная, когда слоты заполнены; если слоты пусты — это зафиксировано в доказательствах, раннер не выдумывается;
- health-check / smoke — по слоту «Верификация» ниже или явной записи в FEATURE;
- доказательства записаны в FEATURE.md; для handoff сессии — кратко в PROGRESS.md.

### Гейты

Все пункты обязательны. Пока любой не выполнен — статус `готово`, закрытие completed и нормальная запись в ranking **запрещены**.

- [ ] Все критерии приёмки отмечены; у каждого заполнены все поля схемы (критерий, команда/действие, результат, артефакт, дата/сессия).
- [ ] У каждого отмеченного уровня верификации заполнены все поля схемы; результат не fail.
- [ ] Если слоты «Тест работоспособности» выше заполнены — базовая верификация зелёная. Если слоты пусты — в доказательствах явно: «слоты пусты» и что проверено вместо этого (раннер не выдуман).
- [ ] В PROGRESS нет открытого блокера по этой фиче, который отменяет заявленный прогон.
- [ ] При `Exec plan:` не «нет» — все этапы до закрытия фичи в статусе `готово` с заполненным DoD этапа (либо фича явно снята / сужена с записью).

Чеклист гейтов дублируется в FEATURE.md («Доказательства DoD»); пустой чеклист = не готово.

### Не считается готовым

- только код / diff / «реализовано» без прогона;
- однословные «ок», «прогнано», «зелёное» без команды, результата и артефакта;
- команда или раннер, которых нет в AGENTS.md / STACK.md;
- подмена отмеченного сквозного / health-check юнитом на моках;
- отключение, skip или ослабление обязательных проверок ради зелёного без записи риска в PROGRESS;
- DoD этапа как доказательство готовности всей фичи;
- `готово` или перенос в completed при пустых / неполных полях схемы;
- оценка A или B в ranking при неполной «Верификации» в result (тогда максимум C — либо сначала добить доказательства).

## Рабочие правила

- Работать над одной фичей за раз;
- Исполнение — по автономному циклу выше: sync на старте; soft решать и продолжать, hard — стоп; при зелёном DoD этапа — commit+push, handoff и стоп, не цепочка этапов;
- Не помечать фичу сделанной, если написан только код;
- Визуальные референсы — папка [refs/](refs/README.md) (пусто допустимо). Перед UI смотреть refs, UIDESIGN, STACK;
- Соблюдать доменные ограничения агента по [docs/convention/index.md](docs/convention/index.md) (канон темы — один файл; точечно SECURITY / UIDESIGN при секретах и UI).

## Окончание сессии

Обновляйте только то, что реально затронули:

- всегда: [PROGRESS.md](PROGRESS.md) (сделано, верификация, риски, следующий шаг);
- если меняли контракт / статус / доказательства фичи: [FEATURE.md](FEATURE.md);
- если есть активный план: файлы в `docs/exec-plans/inprogress/...`;
- если **закрыли** смысловую работу: `docs/exec-plans/completed/` (`*-result.md` с «Оценкой качества») и [docs/exec-plans/ranking/](docs/exec-plans/ranking/index.md);
- [STACK.md](STACK.md) — только если изменился стэк;
- [README.md](README.md) — только если изменилась карта документов или описание проекта;
- при зелёном DoD этапа — commit+push по процедуре выше, затем handoff и стоп; mid-stage и hard — без авто commit/push;
- соседний этап в том же прогоне не стартовать;
- оставьте репозиторий в состоянии, из которого следующая сессия может продолжить по PROGRESS.
